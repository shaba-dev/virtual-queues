# Виртуальные очереди

Сервис восстанавливает очереди к станциям по телеметрии машин (Kafka → Kafka) и рекомендует машине
другую станцию, если там её примут заметно раньше. Плюс симулятор-генератор телеметрии.
Всё на Python 3.10+, ядро расчёта, симулятор и тесты — без внешних зависимостей.

```
telemetry.v1 ──► [ planner ] ──► queue.v1      (ключ station_uuid)
 (ключ unit_uuid)    │      └──► decision.v1   (ключ unit_uuid)
                     └─ снимок состояния ──► vqueue.state.v1 (compact)
```

Подробный разбор кода — в [`MANUAL.md`](MANUAL.md) (что где и для чего), архитектурные решения — в [`ARCHITECTURE.md`](ARCHITECTURE.md), пошаговая проверка на живом Kafka — в [`TESTING.md`](TESTING.md) (bash) и [`TESTING_WINDOWS.md`](TESTING_WINDOWS.md) (PowerShell).

## Запуск

```bash
pip install -r requirements.txt            # только confluent-kafka, нужен для Kafka-части
docker compose up -d                        # один брокер Kafka (KRaft)
python scripts/create_topics.py             # telemetry.v1, queue.v1, decision.v1, vqueue.state.v1

export PYTHONPATH=src                       # или: pip install -e .
python -m vqueue.service   --config config/site.json                  # сервис (отдельный терминал)
python -m vqueue.generator --config config/site.json --speedup 60 \
       --dup-rate 0.02 --late-rate 0.02 --follow-decisions            # генератор, ускорение ×60
```

Те же команды: `make up`, `make service`, `make generator`. Посмотреть результат:
`kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic queue.v1 --from-beginning`.

Генератор: `--speedup 1` — реальный темп, `--speedup 0` — без пауз; `--dup-rate`, `--late-rate`,
`--max-late` (по умолчанию 60 с) — дубли и опоздания; `--follow-decisions` — водители выполняют
рекомендации из `decision.v1` (замкнутый контур); `--stdout` — печать в stdout без Kafka.

**Без брокера:** `python -m vqueue.simulate --minutes 60` прогоняет симулятор через движок и печатает
итоги — быстрый способ увидеть очереди и решения.

## Тесты

```bash
python -m unittest discover -s tests -t . -v      # или: make test; pytest тоже подойдёт
```

90 тестов, около полутора минут, брокер не нужен. Что проверяется:
`test_station_occupancy` — занятие/освобождение станции (первое сообщение «на станции», 230 с,
выход из радиуса, ожидание, приезд = вход в радиус, состояния машины);
`test_queue` — пример из задания цифра в цифру, порядок, горизонт 30 мин, свежесть 30 с;
`test_decisions` — пример `T4 → S2` с выигрышем 80 с, порог 60 с (границы 59/60), ничья, `no_gain`,
`stale_telemetry`, один расчёт за заезд, возврат к своей станции;
`test_order_and_publish` — дубли, опоздавшие, «сейчас» = max `ts`, дедупликация публикаций,
формат JSON из задания; `test_sim` — симулятор (1 с, 10 м/с, 200 с, очередь, шум) и сквозные
инварианты «симулятор → движок», детерминизм и восстановление из снимка;
`test_runner` — раннер на in-memory брокере: рестарт без дублей, падение до коммита, откат коммита,
повреждённый снимок.

## Что сделано

- **Сервис** (`vqueue.service`, `runner`, `kafka_io`): читает `telemetry.v1`, публикует `queue.v1` и
  `decision.v1` на непрерывном потоке. Пакет сообщений обрабатывается и коммитится одной
  Kafka-транзакцией вместе со снимком состояния и оффсетами (см. `ARCHITECTURE.md`).
- **Ядро** (`engine.py`): чистая логика на времени событий, без часов компьютера и без Kafka.
- **Генератор** (`sim.py`, `generator.py`): движение по прямой, 10 м/с, обслуживание 200 с, очередь
  у станции, дубли и опоздания до 60 с, реальный темп или ускорение.
- **Конфигурация** (`config/site.json`): 4 станции, точка разгрузки, 40 машин (14/12/8/6 по станциям),
  константы из задания (`Params`).
- `ARCHITECTURE.md`, `docker-compose.yml`, скрипт создания топиков.

## Как разрешены неоднозначности правил

1. **Приезд считается от времени позиции**, а не от «сейчас»: `eta = ts_позиции + расстояние / 10 м/с`
   (в секундах, округление до ближайшей). При свежих позициях это то же самое, что в примере, но очередь
   не «дрожит», пока «сейчас» двигают сообщения других машин, — иначе каждое сообщение чужой машины
   меняло бы ETA и вызывало публикацию.
2. **Момент занятия**: свободная станция — первое сообщение «на станции» (скорость < 1 км/ч и < 50 м).
   Ждущая машина занимает станцию в момент её освобождения. Освобождение — раньше из «230 с после
   занятия» и «занявшая вышла из радиуса»; применяется лениво по времени событий, таймеров нет.
3. **Машина, простоявшая в радиусе дольше 230 с**, считается обслуженной и повторно станцию не занимает.
4. **Свежесть**: «не старше 30 с» включительно. Устаревшая ждущая машина не может занять станцию
   (иначе станция «занималась» бы призраком); занявшая станцию остаётся в очереди без телеметрии.
5. **Выход из радиуса без обслуживания** (ждущая машина уехала) трактуется как переход «к разгрузке».
6. **Остановка у любой станции** считается нахождением на ней: если водитель проигнорировал
   рекомендацию и встал у своей станции, видим реальность, а не рекомендацию.
7. **«Приедет раньше нашей»** сравнивается по паре `(eta, unit_uuid)` — тот же порядок, что в очереди.
   Очередь для рекомендации берётся с горизонтом 30 мин, как и опубликованная.
8. **`stale_telemetry`** тоже расходует расчёт за заезд (в задании «публикуется на каждый расчёт»).
9. **Холодный старт**: машина, чьё первое сообщение уже ближе 1500 м к станции, получает решение сразу —
   по неполной картине очередей. Первое сообщение вне «на станции» всегда трактуется «к станции» (по заданию),
   даже если машина реально едет к разгрузке: её ETA завышен/занижен до выхода из радиуса точки разгрузки.
10. **Публикация `queue.v1`**: сравнивается содержимое очереди без поля `at`; пустая очередь публикуется,
    когда очередь опустела, но не в начале, когда она и так пуста.
11. Время нигде не берётся из часов компьютера, пока на вход не приходят сообщения, «сейчас» не движется
    и ничего не публикуется (событийное время).

## Что сознательно не сделано

- **Несколько процессоров и несколько партиций входа** — см. `ARCHITECTURE.md`, п. 1, 4 и 7: при 40 сообщениях
  в секунду (движок держит ~8 000 на ядро) это добавило бы хоп, вторую транзакцию и недетерминизм без выигрыша.
- **Подавление повторных решений при полном перечитывании топика** без снимка: решения воспроизводятся
  идентично (тот же ключ и `at`), потребитель должен дедуплицировать по `(unit_uuid, at)`.
- **Метрики/мониторинг** (lag, Prometheus), **схемы** (Avro/JSON Schema), **авторизация/TLS Kafka** — только
  счётчики в логе раз в 15 с.
- **GPS-шум и ускорение/торможение** в симуляторе: движение строго с постоянной скоростью; 30-секундный
  манёвр смоделирован как пауза станции между машинами.
- **Горизонтальное масштабирование по площадкам** описано, но не реализовано (одна площадка в конфигурации).

## Как проверено и чего не проверено

- Тесты и офлайн-прогон выполнены. В симуляторе занявшая станцию машина из расчёта совпадает с реально
  обслуживаемой в 100% замеров (3 590 замеров за 23 минуты после 17-минутного прогрева).
- **Kafka-часть (`kafka_io.py`, `service.py`, `generator.py` в режиме Kafka, `create_topics.py`) в среде
  разработки не запускалась на реальном брокере**: там не было ни сети, ни `confluent-kafka`. Код проверен
  компиляцией и логика коммита/рестарта — на in-memory брокере (`tests/fakes.py`) через тот же `Runner`.
  Транзакции, `on_assign`-восстановление и `docker-compose.yml` нужно прогнать на живом брокере:
  это первое, что стоит сделать (`make up service generator`).
